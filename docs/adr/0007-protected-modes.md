# ADR-0007: Защищённые режимы обработки и локальное восстановление

- **Статус:** принято (поэтапная реализация; на момент принятия реализован срез 1)
- **Дата:** 2026-10-19
- **Основание:** `PROTECTED_MODES_IMPLEMENTATION_FOR_CODING_AI.md`,
  аудит `docs/security/PROTECTION_ASSESSMENT.md`

## Контекст

Сейчас любой запрос уходит выбранному провайдеру целиком: история диалога,
документы RAG, вопрос. Пользователь не может выбрать политику обработки, не
видит, какие данные уходят, и не может отправить контекст без прямых названий
организаций. Аудит (`PROTECTION_ASSESSMENT.md`, HEAD `dcd1c48`) перечисляет
10 пробелов.

Ключевое ограничение: продукт self-hosted, но провайдеры внешние. Значит
«защищённый» режим — это **минимизация и псевдонимизация**, а не анонимность,
и обещать соответствие корпоративным политикам нельзя.

## Решения

### 1. Три режима, выбирает пользователь

| Режим | Что происходит |
| --- | --- |
| `cloud_controlled` (по умолчанию) | отправка разрешена; локально показываются найденные категории данных и предупреждения; пользователь может отредактировать или перейти в гибрид |
| `protected_hybrid` | локально готовится sanitized-контекст; наружу уходят только псевдонимы; ответ восстанавливается локально |
| `local_only` | внешние вызовы запрещены; работают только локальные runtime (Ollama/LM Studio) |

Административных ограничений, ролей и списков «одобренных» провайдеров нет.
Дефолт — текущее поведение, чтобы обновление не меняло смысл запросов.

### 2. Два представления сообщения

`Message.content` остаётся **приватным** (для пользователя и локальных
операций). Sanitized-версия хранится отдельно в `Message.protection` (JSONB) и
именно она уходит провайдеру и используется как контекст следующего turn. Это
прямо закрывает требование «восстановленные значения не уходят обратно в
облако»: история для провайдера строится из sanitized-версий.

### 3. Подготовка и подтверждение (prepare → commit)

Отправка в гибриде состоит из двух шагов:

1. `prepare` возвращает приватный и sanitized preview, `payload_digest`,
   `revision`, найденные сущности и решения (REPLACE_REVERSIBLE / REMOVE /
   GENERALIZE). Ничего не отправляет.
2. `commit` принимает `preparation_id` и `digest`; если digest или revision не
   совпали — отклоняется до сети. Повторный commit идемпотентен и не создаёт
   второй платный вызов.

### 4. EntityVault

Карта «псевдоним → исходное значение» хранится в PostgreSQL, значения
шифруются мастер-ключом приложения (тот же Fernet-контур, что ключи
провайдеров). Псевдонимы стабильны в пределах подготовки:
`[ORG_1]`, `[INN_1]`, `[EMAIL_1]` и т. д. Vault не отдаётся transport-слоем:
в API нет эндпоинта, возвращающего исходные значения; восстановление
выполняется локально при отображении.

### 5. Детекция

Срез 1 — локальные правила без внешних сервисов: regular expressions для
email, телефонов, URL, реквизитов (ИНН, ОГРН, СНИЛС, БИК, расчётный счёт,
паспорт), секретов (ключи вида `sk-…`, `Bearer …`, пароли в тексте), плюс
словарь организаций, который пользователь ведёт сам. NER-модель — отдельное
решение после замеров (ADR при добавлении зависимости).

### 6. Восстановление ответа

- Только точное совпадение псевдонима из vault; поиск по подстрокам запрещён,
  чтобы не восстанавливать случайные совпадения.
- Секреты **удаляются** на этапе санитизации и не попадают в vault, поэтому не
  восстанавливаются даже при явном разрешении: это безопаснее, чем хранить
  пароли и ключи ради возможности их показать.
- Восстановление не применяется внутри URL, Markdown-ссылок и HTML-атрибутов:
  иначе значение попало бы в кликабельную ссылку или картинку.
- Псевдонимы не восстанавливаются рекурсивно: подставленный текст не
  сканируется повторно.

### 7. Локальный режим

`local_only` допускает только провайдеров, помеченных как локальные (явное
объявление типа `ollama`/`lmstudio` с проверкой доступности и без cloud
fallback). В этом режиме дополнительно запрещены веб-поиск, импорт тарифов и
любые внешние инструменты; проверяется отдельно, включая egress.

### 8. Модель без цены

Разрешается использовать: `UsageRecord.cost_amount = NULL`,
`cost_state = unknown`, в UI видно предупреждение, что денежный лимит для таких
запросов не гарантируется. Резерв бюджета для них не создаётся (нет цены), но
факт вызова и usage сохраняются. Защита данных от этого не ослабляется.

## Границы доверия

```text
Пользователь → браузер → API (хост приложения)
                               ├─ PostgreSQL: оригиналы, vault (шифрованный), sanitized-копии
                               ├─ Qdrant / BlobStore: документы и векторы (локально)
                               ├─ sanitized payload ──► внешний провайдер LLM
                               └─ ответ ──► локальное восстановление из vault ──► UI
```

«Локально» = хост приложения. Если приложение развёрнуто на сервере, данные
покидают компьютер пользователя уже при загрузке; UI обязан говорить «на сервере
приложения», а не «на вашем устройстве».

## Последствия

- Появляются новые таблицы и миграция; старые диалоги читаются как
  `cloud_controlled`.
- Нужен feature flag на время разработки (`PROTECTION_MODES_ENABLED`, по
  умолчанию выключен): нельзя показывать рабочий индикатор защиты до готовности
  всех инвариантов.
- Стоимость гибрида растёт по времени (локальная подготовка) и не меняется по
  цене (payload короче).
- Точность детекции не гарантируется: precision/recall публикуются на
  синтетическом наборе как ограничение, а не как обещание.

## Rollback

Выключение `PROTECTION_MODES_ENABLED` возвращает текущее поведение: режимы не
показываются, история читается как облачная. Новые таблицы остаются, данные не
удаляются; миграция обратима удалением таблиц (данные защиты не критичны для
чата).

## Влияние на Этап 2

Отсутствует: контракты `Provider`, `Job`, `Asset`, `UsageRecord`, `BlobStore`
не меняются. Видео-запросы смогут использовать тот же vault при необходимости.
