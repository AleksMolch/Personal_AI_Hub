# ADR-0002: RapidOCR как альтернативный backend OCR в worker

- **Статус:** принято (GO, условный — с обязательным прототипом на фикстурах);
  **реализовано в Итерации 2 (2026-09-21)**;
  **ресурсные измерения закрыты (2026-10-05)**
- **Дата:** 2026-09-21 (замеры: 2026-10-05)

## Измерения ресурсов (2026-10-05, docker/Desktop, x86-64, Python 3.12-slim)

Базовый образ `personal-ai-hub-api:latest` — 780,2 МБ. Все варианты ниже —
одноразовые probe-образы, они НЕ входят в compose и release.

| Ваант установки RapidOCR | Размер образа | Прирост |
| --- | --- | --- |
| базовый образ (без RapidOCR) | 780,2 МБ | — |
| `rapidocr_onnxruntime==1.4.4` + `libgl1` + `libglib2.0-0` | 1445,5 МБ | **+665,3 МБ** |
| `rapidocr_onnxruntime==1.4.4` (opencv-python, без libGL) | 1181,8 МБ | +401,6 МБ |
| `rapidocr_onnxruntime==1.4.4` + `opencv-python-headless` (поверх opencv-python) | 1278,9 МБ | +498,6 МБ |
| **`opencv-python-headless==4.11.0.86` + `rapidocr_onnxruntime==1.4.4 --no-deps` + `onnxruntime==1.30.0` + `pyclipper`/`Shapely`/`tqdm`** | **1109,5 МБ** | **+329,3 МБ** |

Вывод: `libgl1` тянет mesa-стек и стоит ~+260 МБ поверх headless-варианта,
поэтому RapidOCR следует ставить только с `opencv-python-headless`
(без `opencv-python`), иначе в worker-образе нужен ещё и `libGL.so.1`.

Состав прироста в site-packages (probe-образ): OpenCV (cv2 + opencv_python.libs)
188 МБ, onnxruntime 67 МБ, модели rapidocr_onnxruntime 16 МБ.

### Время и память на страницу

Страница A4 при 300 dpi (2480×3508) с плотным синтетическим текстом,
по 3 страницы на движок, первая страница включает инициализацию движка:

| Метрика | Tesseract | RapidOCR |
| --- | --- | --- |
| 1-я страница, с | 1,27 | 2,59 |
| 2-я / 3-я страница, с | 1,03 / 1,00 | 1,33 / 1,96 |
| RSS процесса после OCR, МБ | 88,8 | 192,3 |
| Пиковый RSS процесса, МБ | 187,5 | 822,5 |
| Idle RSS до первого OCR, МБ | 21,8–55,2 | 21,8–55,2 |

Итоги:
- **Idle RAM не растёт** — подтверждено: импорт ленивый, без первого OCR RapidOCR
  не потребляет память (21,8–55,2 МБ в обоих backend);
- RapidOCR на этой фикстуре **медленнее** Tesseract (1,3–2,6 с против ~1,0 с на
  страницу) и заметно прожорливее по пику памяти (~820 МБ против ~190 МБ);
- качество распознавания русскоязычных сканов этими числами не измеряется —
  для этого нужен отдельный fixture с реальным текстом.

Практический вывод: RapidOCR остаётся **опциональным** backend'ом (этап 2
не блокируется). Включать его стоит только под конкретные сканы, где Tesseract
не справляется, и с учётом +329 МБ к образу и ~0,8 ГБ пиковой памяти на
одну страницу. Для базовой установки RapidOCR не нужен.

## Реализация (отклонения от проекта)
- `OcrBackend.recognize` принимает PIL-Image (не путь): модуль
  `packages/core/personal_hub/ocr.py` рендерит/дешифрует картинку заранее,
  единый executor (`max_workers=1`) и per-page таймаут → `OcrError(OCR_TIMEOUT)`.
- `OCR_PAGE_TIMEOUT_SECONDS` — фактическая реализация таймаута страницы.
- Parse документов в worker выполняется в `asyncio.to_thread`, чтобы OCR/рендер
  не блокировали event loop.
- Заодно закрыт billing gap индексации: embeddings резервируются до вызова
  (см. `apps/api/app/billing.py`, `apps/worker/tasks/ingest.py`).
- E2E «скан → OCR → чанки → Qdrant → RAG» сделан с детерминированным
  fake-backend (интеграционные тесты не зависят от системного tesseract);
  негативный тест проверяет `OCR_*` код в статусе документа.

## Контекст
Текущий OCR в проекте — только Tesseract (`pytesseract.lang="rus+eng"`) для
пустых (без текстового слоя) страниц PDF, рендер через `pdf2image`+poppler.
Проблемы:

- ошибки OCR проглатываются (`parsing.py:_ocr_pages` — `except Exception
  : return {}`), деградация молчаливая и не видна в статусе задачи;
- изображения (PNG/JPG/TIFF) как документы не поддерживаются;
- нет лимитов страниц, размера рендера и таймаутов на страницу;
- нет OCR-тестов и фикстур скан-документов;
- для русских/английских полиграфических сканов качество Tesseract
  без проективной преобработки посредственное.

Кандидат RapidOCR (ONNX-рантайм) закрывает эти пробелы и даёт выбор backend.

## Текущее решение
Оставить Tesseract как backend по умолчанию и ввести:

- интерфейс `OcrBackend` (protocol) с методом
  `recognize_image(image_path, languages) -> OcrResult`;
- `TesseractOcrBackend` — обёртка текущего пути без изменения поведения;
- `RapidOcrBackend` — ленивый импорт, запуск только в worker, per-page
  таймаут, ограничение размера изображения, понятная ошибка при отсутствии
  рантайма/моделей;
- настройки `OCR_BACKEND=tesseract|rapidocr|auto`, `OCR_LANGUAGES`,
  `OCR_MAX_PAGES`, `OCR_MAX_IMAGE_SIDE`;
- режим `auto`: сначала текстовый слой, при недостатке текста — OCR;
  если RapidOCR недоступен — fallback на Tesseract;
- ошибки OCR фиксируются в `job.status`/`error_code`.

## Рассматриваемые варианты
1. Оставить Tesseract и только починить молчаливые ошибки и лимиты
   (минимум изменений, но качество сканов не растёт).
2. RapidOCR как альтернативный backend (выбран; риск — рост образа/RAM).
3. OCR от Docling (отклонено: слишком тяжёлые зависимости для этой задачи).
4. Шаблонные проективные преобработки перед Tesseract (как улучшение,
   не отменяющее необходимость RapidOCR; пригодно как быстрый фикс).

## Почему не выбран альтернативный путь
Вариант 1 решает только механику (ошибки, лимиты), но не качество распознавания
сканов и не покрывает изображения. Вариант 3 втаскивает тяжёлую систему ради
задачи, которую закрывает лёгкий ONNX-рантайм. Вариант 2 изолирован в worker
и оставляет Tesseract как full fallback, что даёт безопасный rollback.

## Последствия
- Рост backend-образа измерен: **+329,3 МБ** при установке с
  `opencv-python-headless` (без `libgl1`); вариант с `libgl1` — +665,3 МБ.
  Оценка «~20–40 МБ» из исходного ADR не подтвердилась, цифра исправлена.
- Пиковый RSS в worker на одну страницу: до ~820 МБ (RapidOCR) против ~190 МБ
  (Tesseract); idle RAM не затронут из-за ленивого импорта.
- Время на страницу A4 300 dpi: Tesseract ~1,0 с, RapidOCR 1,3–2,6 с.
- `rapidocr_onnxruntime` зависит от `opencv-python`, которому нужен
  `libGL.so.1`; без `libgl1` в образе RapidOCR падает на импорте с понятной
  ошибкой `OCR_UNAVAILABLE` (в тексте ошибки указывается первопричина).
- Качество индексации скан-PDF и OCR изображений растёт, при условии
  подтверждения на фикстурах.
- Новые env-переменные (`.env.example`), контракт `OcrBackend`.
- Требуется E2E-тест «скан → OCR → чанки → Qdrant → RAG» и негативные тесты.

## План rollback
`OCR_BACKEND=tesseract` полностью отключает RapidOCR-путь; удаление
`RapidOcrBackend` и env-переменных не меняет поведение базовой установки.

## Влияние на Этап 2 (video generation)
Никакого: изменение изолировано в OCR-пути индексации документов (worker),
не трогает контракты `Provider`, `Job`, `Asset`, `UsageRecord`, `BlobStore`
и не блокирует видео-джобы.
