# ADR-0004: LiteLLM только как опциональный внешний proxy (профиль `litellm`)

- **Статус:** принято (GO, вариант A — внешний proxy) для Итерации 3
- **Дата:** 2026-10-05

## Контекст

В проекте уже есть собственный OpenAI-compatible адаптер
(`packages/core/personal_hub/providers/openai_compatible.py`), нормализация
ошибок, billing с `CostReservation`, `UsageRecord` и `PriceSnapshot`. LiteLLM
в assessment получил статус DEFER: он тяжёлый, а основную совместимость с
OpenRouter/RouterAI/Selectel уже обеспечивает наш адаптер.

Однако LiteLLM полезен как локальный шлюз: единые ключи, failover между
endpoint'ами, нормализация usage. Внедрять его как замену provider layer нельзя —
бюджет и тарификация остаются в Personal AI Hub.

## Измерения (2026-10-05, docker/Desktop, x86-64)

| Вариант | Прирост образа | Время/RSS при импорте | Комментарий |
| --- | --- | --- | --- |
| **A: внешний proxy `ghcr.io/berriai/litellm:v1.104.0`** | **+383,1 МБ (сжатые слои), только при `--profile litellm`** | не в backend-процессах | образ не входит в `make up`/`bootstrap`, не качается без профиля |
| B: библиотека `litellm==1.104.0` в backend | +355,3 МБ к базовому образу (780,2 → 1135,5 МБ) | `import litellm`: **5,31 с, +178,5 МБ RSS** | платит каждый процесс, импортирующий пакет |
| C: не внедрять | 0 | 0 | оставляет часть задач пользователю |

Вывод: **Вариант A** — образ не входит в базовую установку, backend не получает
тяжёлых зависимостей и не платит RAM/время импорта.

Проверено вживую: контейнер стартует с `infra/litellm/config.yaml`, отвечает
`/health/liveliness` → `200 "I'm alive!"`, а `/v1/models` возвращает
OpenAI-совместимый список (`litellm-default`).

## Решение

1. **Никакой библиотеки litellm в backend.** Адаптер остаётся
   OpenAI-compatible; новый тип `litellm_proxy` в реестре указывает на тот же
   адаптер, а `ProviderPreset` задаёт `base_url=http://litellm:4000/v1`.
2. **Опциональный compose-профиль `litellm`** с закреплённым образом
   `ghcr.io/berriai/litellm:v1.104.0` (без `latest`). В `docker compose config`
   сервис отсутствует без `--profile litellm`.
3. **Порт наружу не публикуется в WAN:** публикация только на `127.0.0.1`.
4. **Шаблон конфигурации** `infra/litellm/config.yaml` без секретов; ключи
   приходят из `.env` (`LITELLM_MASTER_KEY`, `LITELLM_UPSTREAM_*`).
5. **Команды:** `make up-litellm` / `make down-litellm` — единственный
   пользовательский вход к профилю.

## Рассматриваемые варианты
1. Внешний proxy (выбран).
2. Внутренняя библиотека (отклонено: +355 МБ образа и +178 МБ RAM в каждом
   процессе, tight coupling и breaking changes).
3. Не внедрять (оставлено как допустимое решение: базовый OpenAI-compatible
   адаптер покрывает текущие провайдеры, а профиль можно не включать).

## Последствия
- Базовая установка (`make bootstrap`, `make up`, `make smoke`, тесты) не
  меняется: 0 новых зависимостей, 0 новых миграций.
- Появляется второй источник конфигурации и ещё один сервис в сети стека.
- Провайдер `litellm_proxy` в UI появляется в списке пресетов, даже если
  профиль не запущен: соединение вернёт ошибку `PROVIDER_UNREACHABLE`.
- Цены и бюджет считает Personal AI Hub. Если прокси подменяет модель,
  тарификация останется по нашему профилю цены (фактическая модель прокси в
  `UsageRecord` не сохраняется — это осознанное ограничение Этапа 1), поэтому
  автоматический fallback на более дорогую модель запрещён (см. `AGENTS.md`).

## План rollback
Не включать профиль. Удаление сервиса `litellm` из `compose.yaml` и пресета
`litellm_proxy` из `presets.py`/`registry.py` не затрагивает существующие
провайдеры: это единственные две точки интеграции.

## Влияние на Этап 2 (video generation)
Нейтрально. Для видео по-прежнему проектируются собственные async-generation
адаптеры; если позже понадобится LiteLLM-маршрутизация мультимодальных
задач, контракты `Provider`/`Job`/`Asset` не меняются — добавляется ещё одна
реализация существующего адаптера.
