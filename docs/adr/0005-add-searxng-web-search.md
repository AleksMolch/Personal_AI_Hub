# ADR-0005: Веб-поиск через самостоятельно размещённый SearXNG

- **Статус:** принято
- **Дата:** 2026-10-13
- **Связанные решения:** ADR-0001 (монорепозиторий и стек),
  ADR-0004 (опциональный внешний LiteLLM proxy — тот же приём с профилем)

## Контекст

Модели без доступа к интернету не могут отвечать на вопросы о свежих событиях и
склонны уверенно выдумывать факты. Пользователю нужна возможность обосновать
ответ источниками, при этом:

- платформа self-hosted и работает на собственных ключах пользователя;
- нельзя добавлять обязательную внешнюю зависимость и обязательный новый ключ;
- правила проекта требуют, чтобы любой платный внешний вызов проходил через
  резерв бюджета и `UsageRecord`, а возможности, которых нет, не показывались в
  интерфейсе как работающие.

Рассматривались четыре подхода.

## Рассмотренные варианты

### 1. Встроенный поиск провайдера LLM (OpenRouter `openrouter:web_search`,
### OpenAI Responses `web_search`, Anthropic server-side web search)

Плюсы: не нужен отдельный сервис, источники приходят в нормализованном виде,
usage отдаётся провайдером (можно писать `cost_state=actual`).

Минусы, оказавшиеся решающими:

- OpenAI-инструмент доступен только через Responses API, а адаптер проекта
  работает с `/chat/completions`; через сторонний `base_url` этот инструмент
  недоступен в принципе.
- Anthropic требует собственного Messages API — это отдельный адаптер.
- OpenRouter-инструмент привязан к одному провайдеру, а при «нативном» движке
  вообще не возвращает аннотации (источников не будет), при этом
  `url_citation.content` может содержать целую страницу в markdown.
- Главное: бизнес-логика начала бы зависеть от конкретного провайдера, что
  прямо запрещено правилами проекта.

### 2. Платные поисковые API (Tavily, Brave, Exa, Perplexity)

Плюсы: предсказуемый JSON-контракт, у Tavily есть бесплатный уровень
(1000 запросов/месяц без карты), у Tavily и Exa ответ содержит фактическую
стоимость запроса.

Минусы: требуется новый ключ (ломает модель «только свои ключи»), запросы
уходят третьей стороне (приватность), а `compute_cost` в проекте умеет считать
только токены — для оплаты «за поиск» нужна миграция `PriceSnapshot`. Это
рабочий, но более дорогой и менее приватный путь.

### 3. Собственный скрапер поисковой выдачи

Отклонено: нет контракта, нестабильно, нарушает условия использования
поисковиков. Bing Web Search API закрыт (11.08.2025), Google Programmable
Search закрыт для новых клиентов (миграция до 01.01.2027) — этот путь ещё и
не на что опереть.

### 4. Самостоятельно размещённый SearXNG (выбран)

Плюсы:

- ноль стоимости и ноль новых ключей: SearXNG — meta-поисковик, работающий
  локально;
- запросы не уходят третьей стороне сверх самих поисковых движков;
- **документированный** HTTP-контракт (`/search?format=json`), то есть
  поддержка не строится на догадках;
- провайдеро-независим: работает с OpenRouter, RouterAI, Selectel, DeepSeek и
  любым OpenAI-совместимым endpoint одинаково;
- повторяет уже принятый приём ADR-0004: опциональный сервис в compose-профиле,
  который не влияет на базовую установку.

Минусы (приняты осознанно):

- нужен отдельный контейнер (образ ~98 МБ, качается только с профилем);
- формат `json` в SearXNG выключен по умолчанию: без правки `settings.yml`
  запрос вернёт 403;
- качество и полнота выдачи зависят от доступности внешних движков, часть
  может отвечать CAPTCHA — деградация возможна, поэтому она показывается
  пользователю предупреждением, а не скрывается;
- поиск сам по себе является скрапером, поэтому вопрос условий использования
  отдельных движков не исчезает, а лишь переносится;
- лицензия SearXNG — AGPL-3.0-or-later. Мы **не** модифицируем и не
  распространяем образ, а обращаемся к нему по сети как к отдельному сервису,
  поэтому обязательства AGPL на код проекта не распространяются. При
  необходимости собрать собственный модифицированный образ это решение нужно
  пересмотреть.

## Решение

Веб-поиск реализован как **опциональный локальный сервис SearXNG** с
собственным доменным модулем, не зависящим от адаптеров LLM.

- Новый пакет `packages/core/personal_hub/websearch/`: `base.py` (протокол
  `WebSearchProvider`, DTO `WebSearchResult`/`WebCitation`, ошибка
  `WebSearchError`), `searxng.py` (единственная реализация), `service.py`
  (реестр backend'ов, сборка контекста и системной инструкции).
- Compose-профиль `search`: сервис `searxng` с зафиксированным тегом,
  порт только на `127.0.0.1`, healthcheck; конфигурация без секретов в
  `infra/searxng/settings.yml` (в `search.formats` добавлен `json`).
  Команды: `make up-search` / `make down-search`.
- Настройки: `WEB_SEARCH_ENABLED` (по умолчанию 0), `WEB_SEARCH_PROVIDER`,
  `SEARXNG_URL`, `SEARXNG_TIMEOUT_SECONDS`, `WEB_SEARCH_MAX_RESULTS`,
  `WEB_SEARCH_MAX_CONTEXT_CHARS`, `WEB_SEARCH_ENGINES`.
- API: флаг `web_search` в `POST /conversations/{id}/messages`; эндпоинт
  `GET /api/v1/capabilities` сообщает UI, включён ли поиск, чтобы
  переключатель не рендерился впустую.
- Источники сохраняются в `Message.model_snapshot.web_search.citations`
  (миграция не нужна) и показываются под ответом с той же нумерацией, что и
  маркеры `[n]` в тексте.

### Контроль расходов

Сам поиск бесплатный, поэтому `UsageRecord` для него не создаётся. Расходы
контролируются иначе:

1. **Один поиск на сообщение.** Автоматические «уточняющие» поиски со стороны
   модели запрещены — это аналог запрета на скрытый fallback.
2. **Ограничение контекста**: `WEB_SEARCH_MAX_RESULTS` ×
   `WEB_SEARCH_MAX_CONTEXT_CHARS` задают верхнюю границу добавляемого текста,
   а оценка резерва (`estimate_units`) считается по фактическому тексту запроса
   вместе с найденным контекстом, поэтому лимит бюджета проверяется честно.
3. **Поиск выполняется до платного вызова и до резервирования**: при сбое
   поиска пользователь получает 502, а провайдер LLM не вызывается вовсе —
   покрыто интеграционным тестом.

### Безопасность

- Адрес SearXNG — конфигурация развёртывания, а не пользовательский ввод:
  подставить произвольный хост через API нельзя (SSRF).
- Результаты поиска — недоверенный ввод: они оборачиваются в блок «данные», а
  системная инструкция прямо запрещает выполнять команды со страниц и
  изменять из-за них поведение (защита от prompt injection).
- Ссылки в интерфейсе открываются с `rel="noopener noreferrer"`, текст
  источника выводится как текст.

## Последствия

- Базовая установка не меняется: без профиля `search` сервис не запускается и
  не скачивается, `WEB_SEARCH_ENABLED=0` по умолчанию, переключатель в UI
  скрыт.
- Появляется второй опциональный внешний сервис (после LiteLLM); при отладке
  нужно помнить про два независимых профиля.
- Источники попадают в снимок сообщения: старые сообщения без веб-поиска
  сохраняют совместимость (поле отсутствует).
- Для оплачиваемого поискового backend'а (например, Tavily) потребуется
  миграция `PriceSnapshot` с ценой «за запрос» и расширение `compute_cost`.
  Такой backend добавляется как вторая реализация того же протокола без
  изменения вызывающего кода.

## План rollback

`WEB_SEARCH_ENABLED=0` (значение по умолчанию) полностью отключает
возможность: флаг в API отклоняется, переключатель в UI не рендерится,
сервис `searxng` не запускается. Удаление compose-профиля и пакета
`websearch` не меняет поведение базовой установки.

## Влияние на Этап 2 (video generation)

Отсутствует: решение не затрагивает контракты `Provider`, `Job`, `Asset`,
`UsageRecord`, `BlobStore`. Модуль веб-поиска независим и не блокирует
видео-задачи.
