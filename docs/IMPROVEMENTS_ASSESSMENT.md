# Оценка предлагаемых улучшений (Improvements Assessment)

Назначение документа: итог Итерации 1 из `IMPROVEMENT_TASKS_FOR_CODING_AI.md` —
критическая оценка пяти кандидатов (LiteLLM, RapidOCR, MarkItDown, Docling,
LlamaIndex) против уже реализованного функционала проекта Personal AI Hub,
а также зафиксированные находки ревизии кода (0.1) и решения по каждому
кандидату с вариантами безопасного внедрения.

Функции документа:

- предоставляет go/no-go/defer/prototype по каждому улучшению;
- служит входом для последующих итераций (Итерация 2 и далее);
- является историей решений: что уже умеет проект и почему новая библиотека
  может (или не может) его усиливать.

Дата: 2026-09-21. Автор: coding-агент (Итерация 1, только анализ, без правок
production-кода и зависимостей).

## 0. Ревизия текущей реализации (задача 0.1)

Ревизия проводилась чтением кода и тестов. Изменения в код не вносились.

### 0.1 Provider layer

- OpenAI-compatible adapter реализован один раз в
  `packages/core/personal_hub/providers/openai_compatible.py` и через реестр
  (`providers/registry.py`) назначается всем типам провайдеров
  (`openai_compatible`, `openrouter`, `routerai`, `selectel`).
  Пресеты провайдеров — в `providers/presets.py`.
- Контракты в `providers/base.py`: `ProviderConnection` (provider_type,
  base_url, api_key), `ChatRequest`, `ChatProvider`, `EmbeddingResult`,
  `RemotePricing`, `RemoteModel`, `HealthResult`, enum `Capability`.
- Credentials хранятся в PostgreSQL (`ProviderCredential.encrypted_secret`),
  шифруются мастер-ключом (`security/crypto.py`, `get_cipher()`); наружу
  попадает только маска. `api_key` расшифровывается на момент запроса.
- Streaming: задана генерация через `apps/api/app/chat_worker.py`
  (`run_generation`), события `started/content.delta/completed/failed`
  отдаются по SSE через `apps/api/app/api/generations.py` (`/events`),
  с буфером событий для replay и heartbeat.
- Ошибки нормализуются в `providers/errors.py` (`normalize_http_status`):
  стабильные коды для 401/402/403/404/408/429/5xx.
- Usage и cost: постобработка в `apps/api/app/billing.py` — резервирование
  бюджета до вызова, settlement по фактическим токенам в `UsageRecord`.

### 0.2 Billing layer

- Через budget reservation проходят **только чат-генерации**: `POST
  /conversations/{id}/messages` (`apps/api/app/api/conversations.py`) вызывает
  `check_and_reserve` (цена обязательна, `estimate_units`, TTL резерва 300 с)
  до запуска `run_generation`; фактические токены финализируются после ответа.
- Вызовы, **обходящие billing**:
  - embeddings при индексации документа — `apps/worker/tasks/ingest.py`
    вызывает `adapter.embed(...)` напрямую (батчами по 32), без резерва
    бюджета и без `UsageRecord`;
  - embedding запроса при RAG-запросе —
    `apps/api/app/api/knowledge.py` `query_knowledge_base` →
    `adapter.embed(...)`;
  - RAG-synthesis — `knowledge.py` `_synthesize` → `adapter.chat_complete(...)`
    без резерва, без UsageRecord и без маски лимита бюджета.
- Отдельного пути для embeddings нет: это тот же adapter, но вне
  бюджетного контура. RAG-synthesis — это полноценный платный чат-вызов
  без контроля бюджета.

### 0.3 Document ingest

- Реальные форматы: TXT/MD (plain utf-8), PDF (text layer через pypdf), DOCX
  (paragraphs + таблицы через python-docx). CSV/XLSX обрабатываются отдельным
  table-модулем (DuckDB), в document-пайплайн не входят.
- Text extraction: `packages/core/personal_hub/parsing.py` — per-page `TextPage`.
- Chunking: `chunking.py` — фиксированное скользящее окно 2000 символов с
  overlap 200 (~500 токенов), без учёта структуры документа.
- Embeddings вызываются в worker (`ingest.py`), после parse и chunking.
- Chunks сохраняются в PostgreSQL (`Chunk`: content, position, page, checksum,
  vector_id) и в Qdrant (payload document_id/kb_id/page/position); citations
  собираются из payload + `Chunk` при запросе.

### 0.4 OCR

- Tesseract используется только в `parsing.py` `_ocr_pages`: для пустых
  (без text layer) страниц PDF; `pytesseract.image_to_string(lang="rus+eng")`,
  рендер страниц через `pdf2image` (poppler). В образ ставится `tesseract-ocr`
  + `tesseract-ocr-rus` + `poppler-utils` (см. `apps/api/Dockerfile`).
- Полный сценарий OCR → text → chunks → Qdrant → RAG технически существует,
  но не покрыт тестами и не имеет фикстур сканов.
- Изображения (PNG/JPG/TIFF) как документы не проходят: в `SUPPORTED_EXTENSIONS`
  нет image-форматов, в UI `accept=".txt,.md,.pdf,.docx"`.
- Любая ошибка OCR проглатывается (`except Exception: return {}`) — при
  проблемах с tesseract/poppler документ молча индексируется с пустыми
  страницами; в job не выводится код ошибки. Нет лимита страниц (`OCR_MAX_PAGES`)
  и размера рендера, нет таймаутов на страницу.
- Тестов OCR нет вообще: `tests/unit/test_parsing.py` покрывает только
  TXT/MD/DOCX/unsupported; PDF-пути (текстовый слой и OCR) не тестируются.

### 0.5 RAG

- Retrieval: embedding запроса → поиск в Qdrant (COSINE, top_k) → фильтр
  `hit.score >= MIN_RELEVANCE` (`knowledge.MIN_RELEVANCE = 0.30`).
- Synthesis: `_synthesize` собирает контекст из citations (название + стр.)
  с требованием отвечать по фрагментам; **не биллится** (см. 0.2).
- Reranking отсутствует (ищется только заданный top_k без пересортировки).
- Оценка достаточности — только порог cosine; LLM-проверки нет.
- Тестов качества retrieval нет: integration-тесты
  (`tests/integration/test_knowledge_api.py`) используют фиксированные
  векторы-заглушки `[1.0, 0.0, 0.0]` для всех текстов, т.е. не проверяют
  ранжирование; golden-фикстур для retrieval отсутствуют.

### 0.6 UI

- Страницы: dashboard (`/`), chat, knowledge, jobs, models, providers, usage,
  tables, login.
- Knowledge-страница позволяет: создать БЗ (выбор embedding-модели), загрузить
  документ, задать вопрос (выбор chat-модели), видеть citations + sufficient.
- Настроек OCR/parser/rerank у пользователя нет; конфигурация таких вещей,
  если появится, — через env (в `config.py` новых полей нет).

### 0.7 Сквозные находки (важно для любых решений)

1. **Billing gap для embeddings и RAG-synthesis** — реальный риск списания
   средств без контроля бюджета (см. 0.2). Это нужно закрыть независимо от
   выбранных библиотек.
2. Молчаливые ошибки OCR противоречат правилу «не проглатывать исключения»
   (AGENTS.md) и маскируют деградацию качества индексации.
3. Отсутствует `OCR_BACKEND`/`DOCUMENT_PARSER` выбор и ограничения ресурсов
   OCR (страницы, размер, таймауты).
4. Нет OCR-фикстур и E2E-теста «скан → RAG», нет golden-тестов parsing.
5. Нет reranking и варианта «недостаточно оснований» через LLM.
6. UI не имеет управления новыми возможностями (появятся страницы/настройки
   в соответствующих итерациях).

## 1. LiteLLM

### Что она должна усилить
Provider layer: совместимость с нестандартными API, fallback между endpoints,
централизованный retry/rate-limit, стабильный streaming/usage parsing, будущая
маршрутизация (включая возможный video/multimodal routing на Этапе 2).

### Что уже реализовано в проекте
Собственный OpenAI-compatible adapter на все четыре типа провайдеров,
нормализация ошибок, streaming через SSE, резервирование бюджета до вызова
и settlement по фактическому usage (chat), парсинг цен за токен, тесты
adapter'а.

### Дублирует ли она текущий функционал
Да, в значительной степени: abstraction провайдера, error mapping, usage
accounting (частично) уже есть. Budget-контур в любом случае должен остаться
в нашем backend, т.е. LiteLLM не заменяет billing, а добавляет прослойку.

### Пользовательская выгода
Для MVP (только OpenAI-compatible провайдеры) — минимальная. Новых моделей не
прибавляется; fallback на более дорогую модель запрещён правилами проекта.

### Инженерная выгода
Снижение самописного кода станет ощутимым только при появлении
не-OpenAI-compatible провайдеров (на Этапе 1 таких нет). Как внешний proxy —
дали бы изоляцию, но ещё один сервис и конфигурацию.

### Риски
- Зависимость (прослойка в чужом коде), breaking changes;
- при варианте A — лишний сервис в Compose и точка отказа;
- при варианте B — связывание backend с LiteLLM;
- двойная обработка usage (LiteLLM + наш billing) — риск расхождения;
- конфликт с нашим запретом hidden fallback после принятия задачи.

### Альтернативы
Усилить текущий adapter точечно: добавить retry-with-backoff и работу с
нестандартными полями usage по необходимости, без новой зависимости.

### Решение
**DEFER.** Текущий adapter проще и предсказуемее, покрыт тестами; все
провайдеры Этапа 1 — OpenAI-compatible. Вернуться, когда появится реально
несовместимый провайдер или потребуется маршрутизация видео на Этапе 2.
Тогда — только вариант A (optional compose profile `litellm`, provider_type
`litellm_proxy`), с budget, оставшимся в backend, и без удаления текущего
adapter (это соответствует наиболее безопасному варианту из файла задач).

### Минимальный безопасный способ внедрения
Если в будущем будет принято GO: optional compose profile + adapter-обёртка
на существующий OpenAI-compatible код + документация «когда включать». Сейчас
не внедряется.

### Критерии успеха
(при будущем GO) Текущий adapter работает без изменений; LiteLLM выключен по
умолчанию; бюджетный pipeline не затронут; есть негативные контракт-тесты
401/429/5xx через mock LiteLLM.

## 2. RapidOCR

### Что она должна усилить
Качество OCR сканов PDF без текстового слоя, OCR отдельных изображений
документов, распознавание русского/английского, уменьшение мусора в чанках,
улучшение RAG по сканам. Заодно — закрыть текущие дефекты OCR-пути
(молчаливые ошибки, отсутствие лимитов).

### Что уже реализовано в проекте
OCR только Tesseract (rus+eng) для пустых страниц PDF, рендер pdf2image+poppler
в общем образе. Ошибки глотаются. Изображения не принимаются. Тестов нет.

### Дублирует ли она текущий функционал
Нет. RapidOCR дополняет/улучшает OCR-путь, а не дублирует: существующий
Tesseract остаётся как fallback.

### Пользовательская выгода
Конкретно: скан-документы на русском/английском начинают индексироваться
заметно лучше, появляется OCR изображений, ошибки видны в статусе задачи
вместо молчаливой деградации, включается лимит страниц/размера.

### Инженерная выгода
Единый интерфейс `OcrBackend` с выбором backend (`tesseract|rapidocr|auto`),
изоляция в worker (lazy import, без влияния на idle RAM API), явные ошибки
в `job.status/error_code`, ограничение ресурсов (страниц, размера, таймаут).

### Риски
- ONNX-рантайм + модели (~20-40 МБ) заметно увеличивают backend-образ и RAM
  на страницу в worker;
- загрузка моделей при первом запуске — нужен воспроизводимый способ
  (bundled в образе или известный URL с checksum), чтобы не зависеть от сети;
- качество надо подтвердить на реальных фикстурах до переключения default.

### Альтернативы
- Держать Tesseract и только починить молчаливые ошибки + лимиты (быстрый
  фикс, но качество сканов не вырастет);
- Docling OCR (слишком тяжёлый для этой задачи).

### Решение
**GO (условный).** Решает реальные проблемы проекта и не трогает
provider/billing ядро. Перед продом обязателен прототип с сравнением на
фикстурах (скан-PDF ru/en, фото документа, шум) по метрикам: скорость на
страницу, доля распознанного текста, число пустых/мусорных чанков, RAM.
Этап внедрения — Итерация 2 (RapidOCR или MarkItDown; рекомендация —
RapidOCR).

### Минимальный безопасный способ внедрения
1. Ввести `OcrBackend` (protocol) и завернуть Tesseract как
   `TesseractOcrBackend` (без изменения поведения).
2. Параллельно — `RapidOcrBackend` (lazy import, только worker, per-page
   timeout, лимит размера изображения, понятная ошибка при отсутствии
   рантайма/моделей).
3. Настройки `OCR_BACKEND=tesseract|rapidocr|auto`, `OCR_LANGUAGES`,
   `OCR_MAX_PAGES`, `OCR_MAX_IMAGE_SIDE`; в режиме `auto` — text layer →
   OCR → fallback на Tesseract.
4. Тесты: unit (выбор backend, fallback), integration (fixture скан/image → текст
   → чанки → Qdrant → RAG), негативные (timeout, слишком много страниц).

### Критерии успеха
E2E-тест «скан → текст → чанки → RAG-цитата» проходит на российской и
английской фикстурах; Tesseract работает без RapidOCR; RapidOCR не влияет на
idle RAM API; влияние на размер образа задокументировано; ошибки OCR видны
в jobs.

## 3. MarkItDown

### Что она должна усилить
Единый нормализованный вход для chunking (много форматов → Markdown), меньше
специализированных веток парсера, больше поддерживаемых форматов.

### Что уже реализовано в проекте
`parsing.py`: TXT/MD, PDF (pypdf), DOCX (python-docx). Обработка ошибок —
`UnsupportedFormatError` → корректный failed job.

### Дублирует ли она текущий функционал
Частично: для TXT/MD результат эквивалентен; для PDF/DOCX будет параллельная
реализация преобразования, что добавляет второе поведение для одних и тех же
файлов (нужно сравнение и решение о роутинге).

### Пользовательская выгода
Малая на Этапе 1: дополнительные форматы (HTML/EPUB/XLSX→markdown) не входят
в текущие пользовательские сценарии, а таблицы всё равно остаются в DuckDB.

### Инженерная выгода
Один intermediate-формат удобен, но достигается ценой новой зависимости и
абстракции `DocumentParser` + роутинг — это перестройка рабочего пути только
ради унификации.

### Риски
- Добавление зависимости с транзитивными пакетами;
- дублирование веток (builtin vs markitdown) и риск расхождения качества на
  одних и тех же файлах;
- конфликт с табулярным путём (таблицы не переводить в Markdown насильно).

### Альтернативы
Оставить builtin-парсер и добавлять форматы точечно; «структурный» выигрыш
для сложных PDF лучше ставит Docling (тоже DEFER), а не MarkItDown.

### Решение
**DEFER.** Выгода для пользователя минимальна, а введение универсального
нормализованного формата сейчас — рефакторинг без подтверждённой потребности.
Проверить снова, если появятся форматы (HTML/EPUB), которые нужны реальным
сценариям.

### Минимальный безопасный способ внедрения
(при будущем GO) Ввести `DocumentParser` protocol и `MarkItDownParser` как
option с роутингом `DOCUMENT_PARSER=builtin|markitdown|auto`, golden-фикстуры,
builtin-парсер не удалять.

### Критерии успеха
(при будущем GO) Нынешние фикстуры не ухудшились; результат воспроизводим
(snapshot/golden); README объясняет, когда включать.

## 4. Docling

### Что она должна усилить
Структурированный парсинг сложных PDF: layout, таблицы, заголовки/секции,
меньше мусорных чанков, лучшее качество RAG по отчётам и научным документам.

### Что уже реализовано в проекте
Плоский текст pypdf + фиксированный чанкинг по символам; секции/структура
не сохраняются.

### Дублирует ли она текущий функционал
Частично: адресует тот же вход (PDF), но добавляет структуру, которой нет.
Не дублирует табличный DuckDB-путь (ограничение соблюдается).

### Пользовательская выгода
Заметная только для сложных PDF (отчёты, инструкции, статьи): качество
структуры и retrieval. Для простых PDF выгоды почти нет.

### Инженерная выгода
Section-aware chunking (заголовками) вместо фиксированного окна. Но требует
отдельного ветвления чанкинга (`if parsed_document.sections: ... else:
текущий chunking`).

### Риски
- Очень тяжёлые зависимости (ONNX/torch-подсистемы), RAM при индексации,
  рост образа на сотни МБ;
- установка/лицензии транспаков;
- конфликт с OCR/MarkItDown (у Docling свой OCR);
- сложность поддержки в worker.

### Альтернативы
- Оставить текущий парсер (для MVP достаточно);
- точечно улучшить pypdf-извлечение таблиц без тяжёлой зависимости;
- use-case-driven прототип сравнения качества на реальных PDF, после чего
  принять решение.

### Решение
**DEFER.** Ценность не подтверждена пользовательской потребностью на Этапе 1
(нет обращений по сложным PDF), а стоимость (RAM, образ) высока. При появлении
потребности — только optional profile (`COMPOSE_PROFILE=docling`,
`DOCUMENT_PARSER=docling|auto`), отдельный образ, тесты качества на фикстурах.

### Минимальный безопасный способ внедрения
(при будущем GO) Отдельный Docker image/profile; `DoclingParser` возвращает
sections/tables/locations/warnings; чанкинг по структуре — optional branch;
базовая установка без Docling не ломается; размер RAM и образа задокументирован.

### Критерии успеха
(при будущем GO) Сложный PDF даёт измеримо меньше мусорных чанков и лучшую
структуру; пользователь включает enhanced parsing осознанно; rollback =
выключение profile.

## 5. LlamaIndex (точечно)

### Что она должна усилить
Инструменты для оценки RAG (evaluation), optional reranking/retrieval
эксперименты, вспомогательный structured node parsing, benchmarks.

### Что уже реализовано в проекте
Нативный RAG: Qdrant retrieval, свой chunking, citations, synthesis,
`MIN_RELEVANCE`. Тесты качества retrieval отсутствуют (см. 0.5).

### Дублирует ли она текущий функционал
Нет, если используется точечно: не заменяет ни storage (Qdrant не трогаем),
ни citations, ни synthesis.

### Пользовательская выгода
Косвенная и позже: параметры, перенесённые после benchmark, улучшат retrieval
(в частности, отсутствующие сейчас метрики и, возможно, rerank).

### Инженерная выгода
Готовая evaluation-обвязка и альтернативный retriever для объективного
сравнения; снижение самописного кода для экспериментов.

### Риски
- Тяжёлая зависимость; прямой запрет на полную замену текущего knowledge
  layer и на дублирующий индекс;
- риск «расползания» LlamaIndex в production, если не держать его в
  experiments/;
- увеличение RAM и сложность отладки, если использовать не в изоляции.

### Альтернативы
Собрать лёгкий evaluation на текущем pipeline (recall@k на своём наборе)
без новых зависимостей — достаточно для базовой метрики.

### Решение
**PROTOTYPE ONLY.** Только `experiments/llamaindex_rag_benchmark/`: набор
synthetic-документов с ожидаемыми ответами/цитатами, сравнение recall@k,
доли правильных цитат, latency, RAM — против текущего RAG. LlamaIndex не
попадает в production runtime и не в обязательные зависимости. По итогам —
decision report в этот документ.

### Минимальный безопасный способ внедрения
1. Каталог `experiments/llamaindex_rag_benchmark/` (не подключается к
   приложению).
2. Небольшой набор synthetic документов + expected answers/citations.
3. Сравнение текущего RAG vs LlamaIndex по метрикам, результат — в
   `docs/IMPROVEMENTS_ASSESSMENT.md`.

### Критерии успеха
No dependency в production; Qdrant и citations не затронуты; отчёт
содержит вывод: улучшает ли LlamaIndex качество и что стоит перенести.

1. Закрыть billing gap: embeddings и RAG-synthesis должны проходить через

2. Перестать проглатывать ошибки OCR: выводить их в статус задачи.

## Влияние оценочных решений на Этап 2 (video)

- Ни одно решение не меняет контракты `Provider`, `Job`, `Asset`, `UsageRecord`,
  `BlobStore`.
- RapidOCR (если будет внедрён) изолирован в worker и влияет только на
  качество индексации документов; архитектуре видео он не препятствует.
- LiteLLM остаётся deferred до тех пор, пока для видео не потребуется
  не-OpenAI-compatible маршрутизация; даже тогда — только optional profile.
- LlamaIndex-эксперименты не затрагивают production-зависимости.
