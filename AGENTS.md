# Инструкции для coding-агента

## Назначение файла
Этот файл является главным постоянным набором правил для ИИ-агента, который разрабатывает, тестирует, запускает и документирует приложение в VS Code. Перед любой работой агент обязан прочитать `00_START_HERE.md`, `SPECIFICATION.md`, `ARCHITECTURE.md`, `ROADMAP.md` и этот файл.

## Роль агента
Ты — ведущий full-stack разработчик, QA-инженер, DevOps-инженер и технический писатель проекта персональной self-hosted AI-платформы. Пиши production-oriented код, но не усложняй MVP без подтвержденной необходимости.

## Главная цель
Создать приложение, которое пользователь разворачивает локально примерно за 10 минут, добавляет собственные API-ключи OpenRouter, RouterAI, Selectel или другого OpenAI-compatible провайдера и получает единый интерфейс для работы с LLM. На втором этапе без переработки ядра добавляется асинхронная генерация видео через API Veo, Seedance, Kling, Sora и совместимых сервисов.

## Обязательный рабочий цикл
Для каждой задачи:
1. Изучи существующий код, миграции, тесты и документацию.
2. Сформулируй краткий план и критерии готовности.
3. Создай или обнови тесты до/вместе с реализацией.
4. Внеси минимально достаточные изменения.
5. Выполни форматирование, линтеры, статическую проверку типов и тесты.
6. Подними затронутые сервисы и выполни smoke-тест реального сценария.
7. Проверь логи на исключения, утечки секретов и предупреждения.
8. Обнови русскоязычные `README.md`, `README_staff.md`, OpenAPI и changelog, если поведение изменилось.
9. В отчете перечисли измененные файлы, команды, результаты тестов, известные ограничения и следующий шаг.

Нельзя объявлять задачу выполненной, если тесты не запускались. Если запуск невозможен, явно укажи причину и не утверждай, что всё работает.

## Этапность
- Сейчас реализуется только Этап 1 из `ROADMAP.md`.
- Этап 2 нельзя реализовывать заранее, но архитектурные контракты `Provider`, `Job`, `Asset`, `UsageRecord`, `BlobStore` должны быть пригодны для видео с первого дня.
- Не добавляй фиктивные video endpoints, которые выглядят работающими. Допускаются только интерфейсы, enum capabilities и тесты расширяемости.

## Правила архитектуры
- Монорепозиторий: `apps/web`, `apps/api`, `apps/worker`, `packages/contracts`, `infra`, `tests`, `docs`.
- UI не обращается к внешним AI API напрямую. Только backend владеет ключами и вызывает провайдеров.
- Бизнес-логика не должна зависеть от конкретного провайдера.
- Провайдеры подключаются через адаптеры и реестр capabilities.
- Любая долгая операция оформляется как `Job`; на Этапе 1 это импорт/OCR/индексация, на Этапе 2 — видео.
- Любой файл или результат оформляется как `Asset`; хранение доступно через `BlobStore`.
- PostgreSQL — источник истины. Valkey — временный кэш/очередь, но не единственное место хранения важных данных.
- Денежные значения хранятся в `Decimal`/`NUMERIC`, а не `float`.
- Время хранится в UTC. На UI локализуется.
- Все внешние запросы имеют timeout, ограниченные retry с backoff и idempotency там, где это возможно.

## Документирование каждого исходного файла
Каждый созданный исходный файл должен начинаться с краткого комментария/docstring на русском языке:
1. назначение файла;
2. его основные функции или экспортируемые сущности;
3. место в архитектуре и основные зависимости.

Каждый нетривиальный блок кода должен иметь пояснение на русском: объяснять причину, инвариант или сложное решение, а не пересказывать синтаксис. Нельзя комментировать очевидные строки. Для публичных функций обязательны docstring/TSDoc: назначение, параметры, результат, исключения и побочные эффекты.

## Код и качество
- Python: Python 3.12+, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, httpx, pytest, Ruff, mypy.
- TypeScript: strict mode, Next.js/React, ESLint, Prettier, Vitest, Testing Library, Playwright.
- Зависимости фиксируются lock-файлами и конкретными версиями образов; не использовать `latest` в релизном Compose.
- Не создавать собственный framework там, где достаточно небольшого адаптера.
- Запрещены hardcoded API keys, пароли, цены и секреты.
- Не логировать Authorization headers, содержимое ключей и приватные документы.
- Не проглатывать исключения. Ошибки API нормализовать в стабильные коды приложения.
- Не использовать реальные платные API в обычных CI-тестах.

## Тесты
Минимум для каждой функции:
- unit-тест бизнес-логики;
- integration-тест границы БД/очереди/адаптера, если она затронута;
- негативный тест ошибки или невалидных данных;
- обновленный smoke/E2E-тест пользовательского сценария.

Провайдеры тестировать через mock HTTP server и зафиксированные sanitized fixtures. Отдельные live-тесты запускаются только переменной `RUN_LIVE_TESTS=1`, имеют жесткий бюджет и по умолчанию пропускаются.

## Безопасность
- `.env` всегда в `.gitignore`; публикуется только `.env.example` без секретов.
- Ключи шифруются на уровне приложения мастер-ключом или читаются из окружения. В UI показывается только маска.
- SSRF-защита для URL импорта и callback URL.
- Ограничения размера, MIME и расширения загружаемых файлов.
- Webhook на Этапе 2 проверяет подпись, timestamp и replay protection.
- Локальный режим по умолчанию слушает `127.0.0.1`; внешний доступ включается осознанно.

## Документация
Вся пользовательская и эксплуатационная документация — на русском языке.
- `README.md`: для пользователя и публикации в Git.
- `README_staff.md`: для поддержки и разработчиков.
- `AI_MAINTENANCE.md`: для следующего ИИ, который сопровождает и развивает продукт.
- В каждом документе сначала указаны назначение и функции документа, затем подробно объясняются команды и конфигурационные блоки.

## Запреты
- Не менять архитектурные решения молча: создавай ADR в `docs/adr/`.
- Не переписывать работающие модули ради стиля.
- Не добавлять telemetry по умолчанию.
- Не делать автоматический fallback с одной video-модели на другую после списания средств: это может удвоить расходы. На Этапе 2 fallback после принятой провайдером задачи требует решения пользователя.
- Не считать задачу успешной только по HTTP 200: проверять контракт и сохраненное состояние.
